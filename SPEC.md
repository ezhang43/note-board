# BusyAnts (Note Board) — Build Spec v1

Started 2026-10-02, kept current with the app (`CLAUDE.md` rule 8) · Owner: Eric Zhang

## Overview

BusyAnts (built as "Note Board"; the name shows in the browser tab, the installed app and the sign-in screen) is a web-based visual board for notes, checklists and links, in the spirit of Milanote. Version 1 runs in the browser and saves its boards between visits; a person can have several boards, and boards inside boards, and can share a board by link to edit it with others (see "Sharing and editing together"). The published site (https://ezhang43.github.io/note-board/) also syncs every board to the signed-in Google account (any Google account), so the same boards open on every device.

The clickable prototype (`note-board-prototype-reference.html`) is the reference for look and behavior. Where this spec and the prototype disagree, this spec wins.

- **Who it's for:** one person organizing ideas, plans and tasks on a free-form canvas.
- **Version 1 goal:** everything in this spec working reliably, saved in the browser and synced to the owner's account.
- **Not in version 1:** uploading pictures or videos. Pictures and videos from web addresses can be put on the board (see "Pictures, videos and web addresses"). Sharing and real-time collaboration are being built (see "Sharing and editing together").

## Build rules for Claude Code

How Claude Code builds this app (stack, tests first, small steps, keeping this spec current, how work goes live) is in `CLAUDE.md`. This spec says what the app does; `CLAUDE.md` says how it is built.

## Board and navigation

The board is an endless canvas with a dotted 20px grid under a fixed top toolbar.

**Toolbar, left to right:** Boards button (see "Several boards") · the path to the open board, when it is inside another · board name (editable, box sized to its text; in a narrow window it and the path shrink first, the name down to 140px, ending in …, so no button is pushed off) · Undo · Redo · | · "Add": Note · Checklist · Container · | · Color (its menu also holds Auto-color) · Arrange · File · Feedback (signed in only: a speech-bubble icon and the word Feedback; it opens Send feedback, see "Delete your account" and "Send feedback") · | · Appearance (a half-filled circle; opens the menu with the Dark mode switch and the color themes, see "Look and feel"); on the published site, Share (an icon of two people, see "Sharing and editing together") and | · Sign out at the far right (an icon button: an arrow leaving a door, with the tooltip "Sign out"). (| = a thin divider between groups.) In windows up to 1500px wide the toolbar's gaps and button text tighten, so every button, Sign out included, fits a 1280px window, also inside a sub-board. Locally, `npm run dev` with `?signed-in` in the address shows Sign out, to check the fit. **Medium windows** (owner pick, 2026-10-22; windows 600 to 1179px wide, such as an upright iPad or a small laptop): the full toolbar needs about 1160px, so below 1180px Arrange, File, Feedback, Appearance and Sign out fold into one ⋯ button at the right end, after Share (Share, the primary action, stays on the toolbar). ⋯ opens a menu under it with the same rows as the phone's ⋯ menu (Arrange and File and Appearance open inside it); Feedback closes it, a click elsewhere or Escape closes it and puts focus back on ⋯, and Escape in an inner menu closes just that one. At 880px and below Note, Checklist, Container and Color also drop their words and show only their icons; each keeps its name as its tooltip and accessible name (Color's is "Color of selected cards and containers"), and below 660px the board name may shrink to 64px. From 1180px up nothing changes. The toolbar never scrolls sideways at any width; the phone layout (under 600px) is unchanged. Note, Checklist and Container (its accessible name is "New container") look alike: outlined buttons, each with its own icon (there is no Add Link: new cards are notes and checklists only; link cards already on a board, or made by an import, still work as described below). **Arrange** (owner decision 2026-10-16) opens a small menu under it holding Snap to grid, Collapse all, Same width and Clean up, each with its label; the menu stays open while its buttons are used, and a click anywhere else closes it. Escape closes the Arrange or File menu and puts focus back on its button. Arrange and File have no border until hovered. On the published site Share is the one solid honey button. A zoom control (Fit to screen · − · percentage · +) sits bottom-right; Fit to screen (or Shift+1 outside text fields) brings every card and container into view, as large as fits, centered (zooming in up to 100%, or out as far as 30%); clicking the percentage resets to 100% around the center of the screen. Left of it: A− / A+ (text size on cards and containers: twelve steps: Small 90%, Normal 100%, Large 115%, Larger 130%, Huge 150%, Largest 175% (owner request 2026-10-19), then 200%, 225% and 250% (owner request 2026-10-23, "A+ up to 250%"; saved as `enormous`, `giant` and `maximum`, after `largest`), then 300%, 350% and 400% (owner request 2026-10-23, "the font text size can still be increased"; saved as `colossal`, `immense` and `ultimate`, after `maximum`); everything on a card or container grows with the step (see "Everything grows with the A− / A+ text size step" below); the toolbar and the other bars, the side panels and the menus keep their size; remembered on this device, not synced, not undoable; A− / A+ fade at the ends; a value saved by an older version still loads, an unknown one falls back to Normal; the per-text sizes below are separate and unchanged), and, further left, a round ? button that opens a Keyboard shortcuts panel listing every shortcut (also opened and closed by the ? key outside text fields; Escape, the ? key, its ×, or a click outside closes it). While it is open it covers the board like Send feedback does (job 174, U9): no board key acts behind it (Delete with a card selected leaves the card alone), the keyboard moves into it when it opens, Tab never reaches the board, and closing puts the keyboard back where it was (on the ? button when that opened it). Right of ?: a round coffee-cup button, "Buy me a coffee", that opens the owner's Buy Me a Coffee page (https://buymeacoffee.com/ezcookie) in a new tab; on a phone it is in the ⋯ menu. Left of ?, one pill holds the side-panel buttons, each an icon with a short label (owner decision 2026-10-16): Search (opens Find), Completed (the Completed panel, see "Clean up and the Completed panel"), History (Version history), Timer (the Focus timer, see "Focus timer"; while it runs it shows the time left instead) and, for someone signed in, Calendar (Google Calendar, see "Google Calendar") and, for everyone, Journal (opens the Journal panel with today's note, see "Daily journal"; owner request 2026-10-18) and, last, Habits (opens the Habits panel, see "Habits"; owner request 2026-10-19). So, left to right: the panel pill · ? · coffee cup · A− / A+ · zoom. **Beside an open side panel** (owner request 2026-10-21, job #130) the whole bar sits in the room left of the panel, right-aligned, and every control stays fully visible and clickable, whatever width the panel has been dragged to: when that room is under 1120px the pill's buttons drop their words and show icons only (each keeps its word as its accessible name and its tooltip; the Timer shows its time left as usual), and when it is under 600px (a panel dragged nearly as wide as it goes) the bar also wraps into rows, the pill on top and ? · coffee cup · A− / A+ · zoom below it (on a very narrow strip the last ones drop to a third row). The two limits are fixed widths worked out for the signed-in bar, so someone signed out may see icons a little earlier than strictly needed. With a wide window, or no panel, nothing changes; the phone layout has no such bar.

- The cursor is the normal arrow on the board and on cards and containers, and a closed glove only while the board is being dragged with the left button from empty space (owner request 2026-10-23, job 193; job 188 had put the glove on the middle button, replacing the Hand tool's open glove); drawing the selection box keeps the arrow. Text fields show the text cursor. The one exception on blocks (owner decision 2026-10-21): over a card's or container's edge and corner grab areas (see Resizing) the cursor is a resize arrow (left-right, up-down or diagonal) and nowhere else on the block, like the calendar panel's resize strip.
- New cards and containers never appear on top of existing blocks. From a toolbar click they appear at the free spot nearest the middle of the screen.
- Edge panning: while dragging a block, dragging checklist items, selecting items by press-and-drag, or drawing a selection box, holding the pointer within 48px of the edge of the board area keeps moving the board that way (faster nearer the edge), and the drag carries on as if the pointer had moved. A drag that starts near an edge only does this once the pointer has been away from the edges.
- Alignment guides: while dragging a card or container (or several selected ones together, which line up as one: the box around them all), when its left edge, middle or right edge (or top, middle or bottom) comes within 8px of the same line of another block on the board, it snaps onto that line and a thin amber guide shows across both blocks. A guide wins over the grid on its axis. Blocks the dragged one is on top of are left out (they are about to move aside). Not while resizing (sizes match instead).
- Add Note, Add Checklist and New container can also be dragged from the toolbar onto the board. A dashed outline shows where the block will appear (the free spot nearest the pointer); a new card dragged over a container goes into the container at the pointer (a new container never does). Letting go off the board adds nothing.
- Opening the board (desktop and phone) shows every card and container, centered on the screen. The remembered zoom is kept when everything fits at it; otherwise the board zooms out just enough, but not below 50% so text stays readable. If the board is still too big at 50%, its top-left part is shown. This also happens when the online copy first arrives on an empty screen. The tool always starts as Hand.

### Several boards

- There can be any number of boards. The first board is the **home board**, which can't be deleted. Each board has its own cards, containers, name, Snap setting and undo history: Ctrl+Z never undoes something on another board (except in the Journal panel, where it undoes on the Journal board only; see "Daily journal"), and switching away and back keeps a board's undo history (until the page is reloaded).
- **Boards button** (a two-boards icon at the left of the toolbar, after the ant; on a phone, in the top bar) opens a menu listing every board (except the hidden Journal and Habits boards, see "Daily journal" and "Habits"): the home board first with the boards inside it indented under it (and theirs under them), then each board that isn't inside another. The open board is highlighted. Clicking a board opens it. Every board except home has a × that deletes it, after asking (“Delete “Trip”?” · Keep board · red Delete board; see "Questions and the Undo message"), since Ctrl+Z can't bring a deleted board back (Version history can).
- **Add a sub-board here** (in the menu; on a phone also + → Sub-board) makes a new, empty board inside the open one: a **board card** appears on the open board (placed like a new card: into a selected container, else at the free spot nearest the middle of the screen), selected. A board card shows the board's name ("Untitled board" until it is named), how many cards are on it, and **Open board**; double-clicking the card opens it too. It can be moved, put in a container, collapsed (showing the name), resized, copied (the copy opens the same board), and deleted like any card: deleting the card leaves the board itself in the Boards menu.
- **New board** (in the menu) makes a new, empty board on its own (not inside another) and opens it. A new board that is left empty and unnamed, and that no card opens, is dropped when another board is opened.
- **New from a template…** (in the menu, under New board) opens the "Start a board" dialog (see "Templates and the example board").
- Opening a board shows every card and container on it, as when the app opens. Which board is open is remembered on each device (not synced), so the app reopens there.
- **Path back up:** on a board inside another, the boards above it show before its name, smaller and grayed ("Home › Trips ›"); clicking one opens it.
- **Ctrl+arrow keys switch boards** (not while typing in a text field; the Control key, not ⌘): Ctrl+→ / Ctrl+← open the next / previous board in the Boards menu order, sub-boards included (as if the whole list were open), passing over the hidden Journal and Habits boards (see "Daily journal" and "Habits"); Ctrl+↑ opens the board above (the one before the name in the path); Ctrl+↓ opens the first board inside the open one. At the ends, and with no board above or inside, nothing happens (no wrap). A short note (the same banner as other notes, gone after about 2.5 seconds) says "Switched to <board name>". They are listed in the ? shortcuts panel. On a Mac, Control+arrows are usually taken by the system (Spaces), so they may never reach the page.
- **Deleting a board** removes it and every board card that opens it, on every board; boards inside it are kept and then stand alone. Every board is saved in Version history first, so a deleted board can be brought back from there. If the deleted board is open, the board above it opens. A shared board is the exception: only the person who shared it can delete it, and it is deleted for everyone (see Sharing and editing together); a "couldn’t be deleted" note shows if that fails.
- Ctrl+A, Clean up, Collapse all, Fit to screen, Download as text, Download as picture (PNG) and Download as PDF work on the open board only; Search too, unless its "All boards" switch is on (see "Search"). Copy and paste work between boards.

### Templates and the example board

Owner request, 2026-10-22 (job #162, from the market research; owner picks: a gallery opened from one row of the Boards menu, and template tiles on an empty board, with the six templates and the example as drafted). A few ready-made boards, so a new person does not start from a bare screen. Each is an ordinary board in the saved format (the same shape a backup holds), so nothing about saving, sync, backups or undo changes; a board made from one is saved, synced, backed up, shared and undone like any other. All text is made up, in plain American English, with no private details and no link cards.

- **The six templates** (each four containers side by side, 20px apart and on the grid, opening fitted on the screen): **Weekly plan** (Top 3 this week, Monday to Wednesday, Thursday and Friday, Weekend), **Project plan** (Goal and team, To do, Doing, Done), **Trip plan** (Before we go, Packing, Day by day, Ideas and maybes), **Reading list** (Want to read, Reading now, Finished, Favorite lines), **Mood board** (The feeling, Warm, Fresh, Calm) and **Study plan** (This term, This week, Exam prep, Done). Their notes and checklists hold a few friendly prompts to change; at most two items are ticked, so ticked items (struck through in place) can be seen.
- **The example, "Weekend in Lisbon"** (the board in the About page's pictures: Before we go, Saturday, Sunday, Ideas, with some items already ticked). It always opens as a board of its own and never replaces anything.
- **On an empty board** (no card or container; a kept Completed record doesn't count; not while an old version is shown), the one-line hint is replaced, in the middle of the board, by a small icon, the title "Start from a template", "Pick one, then change anything you like.", six tiles (three across; two across on a phone), the example as a honey strip ("Weekend in Lisbon", an Example badge, "Open"), and underneath the old hint ("Or add a note, a checklist or a container from the toolbar, or drag one onto the board. Press ? for keyboard shortcuts."; on a phone "Or tap the Add button (+) below to add a note, a checklist or a container."). Each tile shows a small drawing of the template's containers and cards (drawn from the template itself, so it follows dark mode), its name and one line. It scrolls on a short screen (a scroll over it scrolls it only then; otherwise it pans the board as usual), and a press on a tile picks it instead of panning the board; the rest of the empty board pans and zooms as before. Adding any card or container makes it go. A new person sees it right after the welcome tour; the board itself stays empty and theirs until a tile is picked (nothing is saved or synced at first start).
- **Picking a tile on an empty open board fills that board** and fits it on the screen, as one undo step (Ctrl+Z gives the empty board back). The board is named after the template unless it already has a name of its own ("My first board" or no name counts as no name). Everything else about the board stays as it was (Snap setting, the home board stays home).
- **Picking one on a board that has cards** (only from the dialog below) makes a **new board on its own** from the template and opens it; the open board is not touched. Like New board, it is not undone with Ctrl+Z, and it is not dropped as an empty board, since it has cards. Two boards made from the same template have their own cards.
- **"Start a board" dialog**: opened by "New from a template…" in the Boards menu (also on a phone, in the Boards menu in the top bar). The example strip first, then "Templates" and the same six tiles, then "Or start with nothing." and a Blank board button (makes a new empty board, as New board). A modal dialog (a bottom sheet on a phone, 44px targets): focus starts on the first tile, Escape, the × button or a press outside close it, and focus goes back to the Boards button. Picking anything closes it.
- A short note says what happened ("Started “Weekly plan”", or "Opened “Weekend in Lisbon”"), in the same banner as other notes.
- Look and motion: the shortcuts panel's look, the app's colors and radii only; a pressed tile shrinks a little like the buttons, hover only where a mouse hovers; the dialog fades and grows in like the other panels (off with reduced motion and while keys are in use).

### Daily journal

Owner request, 2026-10-18 (first a button that opened a board called "Journal"; changed the same day: "the journal shouldn't open up in a new board, rather it should open up in a side panel like the pomodoro"). The writing is kept on an ordinary board called "Journal", one dated note card a day, so saving, sync, undo and backups work as for any board; the Journal button shows it in a side panel instead of opening that board.

- **Journal button** (a closed book with the label "Journal"): in the panel pill by the zoom control, just before Habits; on a phone a Journal tile in the ⋯ panel's top tiles, just before Habits. Pressing it opens the **Journal panel** in the side panel spot, shared with Version history, Completed, the Focus timer, Google Calendar and Habits (one at a time; full screen on a phone). Escape (a first Escape leaves the text box), its × or the button again closes it. The board being looked at stays open behind it: nothing is opened, moved or selected on it.
- **The panel** shows today's note first, with the cursor at the end of its text, ready to type, and the earlier days below it, newest first. The panel is a **page and a timeline** (owner pick, mockup A, 2026-10-22, jobs #166 and #167). Today's note is a **page** on top, a white sheet (dark in dark mode): its date as the heading ("Wednesday, 21 October", 17px, a button that folds the note, see "Folding a day") with "Week 43" (the ISO week number) at its right, then the rich text box (below, 16px, growing with its text), and under it the word count ("48 words", "1 word"; list markers are not words) and "✓ Saved", which fades in once a change has been written and out after about 1.5 seconds. An empty note for today shows "Write about today…" in gray. The earlier days are a **timeline** below the page (see "Groups"): each day a row with its day number (20px, bold) over its weekday in capitals (11px) on the left and, on the right, the first lines of what is written (15px, up to two lines, cut with …); a click opens the day in place as a white sheet with its rich text box, where it can be edited too. A later date written ahead comes after today's groups, in its own group (see "Groups"); today's note is the one that gets the cursor. Keys pressed while the keyboard is anywhere in the panel (a text box, its heading or blank space, which a click keeps it in) never act on the board behind it (Delete, arrows, copy and paste, Ctrl+D and the like do nothing there); only Ctrl+Z / Ctrl+Y (below) and the zoom keys work. Opening the panel clears the selection on the board, so nothing selected there can be deleted by a key meant for the journal. The heading is the note's first line and is not edited in the panel. Notes on the Journal board without a date line are not shown.
- **Groups** (owner request, 2026-10-19): the days are grouped **Year > Month > Week**, newest first at every level, except that today's year comes first, then today's month within it, today's week within that month and today's day within that week, even when days are written ahead (owner choice "journal fix", 2026-10-20), each group under a header that is a button (it has `aria-expanded`, a keyboard focus ring, and opens and shuts with a click, Enter or Space; a small arrow turns to show which). Weeks run Monday to Sunday, as in the calendar, and are named by their days in that month ("12–18 Oct"). A week that spans two months is split: each month lists its own days under its own part of the week ("28–30 Sep" under September, "1–4 Oct" under October); the same at New Year. A shut group's days are not shown at all.
  - **Look** (owner pick, 2026-10-22): this year has no header of its own (a year other than this one keeps its header, a button like the others); a month header shows how many entries it holds ("13 entries"); a week's name is written in capitals with a thin line after it and, only while the week is shut, how many entries it holds. Today's note is on its page above the groups and not in them, so shutting its month or week never hides it, and a group that would hold only today's note isn't shown. A group header's name for screen readers is just its name (the counts are left out).
  - **Open when the panel opens:** the current year, the current month and the current week (the part of it in the current month) are open, so today is visible; everything older is shut. Days written ahead sit in their own groups, shut.
  - **Remembered on this device only** (`localStorage`, key `note-board:journal-open`, not in the board's data): what the person opens or shuts is kept after a reload. It is not synced, not in backups or Version history, and not undoable. Only choices that differ from the default are kept; missing or damaged saved data falls back to the defaults. Opening the panel always opens the groups holding today again, even if they were shut, so today's note is there for the cursor.
  - **Folding a day** (owner request, 2026-10-21): each day's date line is a header button like the group headers (the same small arrow, `aria-expanded`, keyboard focus ring, click, Enter or Space, and the look), and it folds that day's note. A folded day shows its day number and weekday and, after them, the first line with words of what is written under the date, in the text color and cut after two lines with … when it is too long (nothing after them if the note is empty); today's page folded shows its heading and that line. Unfolding shows the note, ready to edit. Today's note is open and every earlier day is folded when the panel opens (owner pick, 2026-10-22: the timeline's two-line previews are the folded days; before, every day opened); today's note can be folded too. Folds are view state: not saved on the device, not synced, not in backups or Version history, not undoable, and not remembered, so closing and opening the panel (or a reload) opens today's note and folds the earlier days again; shutting and opening a group above keeps a day's fold for that visit. Folding never changes the note's text. Folding the day that holds the text cursor takes the cursor to that day's header. On a phone the header is at least 44px tall.
  - **Width:** on a computer the Journal panel is as wide as the Calendar panel's Week view starts out (420px, the same value), keeping 300px of board beside it in a narrow window. On a computer it can be resized like every side panel (see **Panel width** under Google Calendar). On a phone it fills the screen as before.
- **The Journal board** is the first board named exactly "Journal" (capital J, nothing else) among the person's own boards, in the Boards menu order. A board held by a share (their own shared boards, or ones shared with them) is never used. If there is none, the first press makes one, on its own: no card is added to home or any other board. While it isn't yet known which boards are shared (published site, just after opening), the button changes nothing and says "Your shared boards are still loading. Try again in a moment."
- **Hidden:** a Journal board that no card opens and that holds only dated notes (no containers, no other cards) is not listed in the Boards menu, and Ctrl+arrow keys pass over it, unless it is the open board. While it isn't yet known which boards are shared, nothing is hidden. A Journal board that has a card opening it (as the Journal button used to make, on home) or anything else on it stays listed and opens as any board does.
- **Today's note** is a note card whose text starts with today's date in the calendar's style with the year, on its own line ("Sun 18 Oct 2026", local time), then a blank line; what is typed in the panel goes under the date. Opening the panel adds it if it isn't there: straight above every other block on the Journal board, level with the leftmost one, so the newest day is on top and nothing moves (as it grows, the notes below are pushed down as usual when that board is drawn). A note whose first line is today's date followed by a space and more text (a title typed after the date) counts as today's note; changing the date on the board makes it another day's note, and the next opening adds a new one.
- **Undo:** the Journal board keeps its own undo history, as every board does. Adding today's note is one change and typing is merged as on the board. Ctrl+Z / Ctrl+Y while the keyboard is in the panel undo and redo on the Journal board only, whichever board is open behind it; Ctrl+Z on the board itself undoes that board as usual. Undo in the panel never changes another board.
- **Rich text** (owner request, 2026-10-19; only in the Journal panel, every other text box stays as in "Text formatting"). A **Formatting** bar stays at the top of the panel and acts on the note last typed in: Bold, Italic, Underline, Strikethrough, Bulleted list and Numbered list buttons (pressed while the cursor or selection has that look), a highlighter button ("Highlight yellow": puts the yellow highlight on the selection, or takes it off when it has it) and an **Aa** button ("Text style") that opens one small menu (a press outside, Escape or the button again shuts it, and the cursor stays in the note; owner pick 2026-10-22, replacing four drop-down boxes) with four labeled groups of buttons, the selection's choice pressed (none is pressed when the selection has more than one, "Mixed", so any choice acts): **Style** (Normal, Heading 1, Heading 2, for whole lines; none pressed on a list line), **Text size** (Small, Normal, Large), **Font** (Plex Sans, Serif, Rounded, Handwritten, Typewriter, each written in its own typeface) and **Highlight** (four color dots, Yellow, Green, Blue, Pink, softer in dark mode, and None). The bar's buttons are quiet 32px icon buttons with thin separators, no borders. The Journal's highlight is the one place words get a color (an exception to "No colors" below). Using the bar keeps the cursor and the selected words in the note. Looks apply to the selected words; with nothing selected, to what is typed next at the cursor. Bold, italic, underline and strikethrough turn on for all of the selection unless all of it already has it, then off. Keys while typing in the panel: Ctrl+B / Ctrl+I / Ctrl+U, Ctrl+Shift+X strikethrough, Ctrl+Shift+8 bulleted list, Ctrl+Shift+7 numbered list (a list button on lines that already are that list makes them plain lines again).

Enter at the end of a heading starts a plain line.

Typing in the note on the Journal board itself (it is a plain note there) drops its formatting, which Ctrl+Z on that board brings back.

Formatting that is loaded or imported is checked: only the looks above are kept, and its words are always shown as words, never as markup. Notes without formatting are saved exactly as before, and notes already saved open unchanged.

### Importing from other apps

**File** (toolbar; on a phone under ⋯) opens a menu:

- **Download backup:** every board (every card, position, size, color and setting) in one file, named like "BusyAnts - Home - 2026-10-05.json" ("All boards" in place of the name when there are several).
- **Download as text:** the open board as readable Markdown (a board card is written as "Board: its name"): its name, each container (left to right) with its cards, then the loose cards top to bottom, then the Completed history if there is one (the record Clean up keeps); to-do items as "- [ ]" / "- [x]", sub-items indented, the later lines of a multi-line item indented under it; "[" and "]" in a link's title are escaped.
- **Download as picture (PNG)** and **Download as PDF** (job #163, owner pick 2026-10-22: "save a board as an image or PDF to send or print"): the open board's whole content area as it looks now, in its color theme and in dark mode. Every card and container is in it, not only what is on screen, with a 40px margin all round; the toolbar, panels, selection outlines, resize handles, trash cans, drag handles and the dot grid are left out. The picture is drawn at 2x (less for a huge board, so it stays under what a phone can draw: about 16 million pixels in all, 16,000 on a side); the PDF is one page the size of the board (96 pixels to the inch, shrunk only if a PDF reader would refuse the page) holding that picture, so its text can't be selected. Named like the backup: "BusyAnts - Home - 2026-10-22.png" / ".pdf". A picture from another site that the browser won't let the page copy (most web pictures) is drawn as a light blank panel instead, a video or web page (YouTube...) as a blank 16:9 panel; neither stops the download. While it is drawn the notice banner says "Preparing…"; an empty board says "Nothing on this board to save yet." and a failure says "Couldn’t make the picture. Try again, or try a smaller board." The drawing code (the small MIT-licensed html-to-image package) is loaded only when one of these is chosen. **After the site is updated** (review 181 C-L7, owner OK 2026-10-22), a page opened before the update can no longer download that code, or the PDF reader's code (Import file…) — the old files are gone. Instead of "Couldn’t make the picture" or "BusyAnts can’t read that file yet.", the notice banner says "BusyAnts was updated. Reload the page to use this." with a Reload button (before Dismiss) that reloads the page; the board comes back as it was saved. A failed download with no connection says the same.
- **Restore from backup…:** pick a backup file; after asking ("Replace this board with the backup?" · Cancel · Replace board) it replaces the board. A backup of one board, with one board here, replaces the open board: the board as it was is saved in Version history first, and Ctrl+Z brings it back. A backup of several boards (or any backup while there are several boards here) replaces every board, after asking "Replace all your boards with the backup?" (· Replace all boards): every board is saved in Version history first, and undo starts over. A backup made before there were several boards replaces the open board. A file that isn't a BusyAnts backup changes nothing and says so in the note banner. The restored board is brought into view. Boards someone else shared with this person (the shared board and every board inside it) are never replaced or removed by a backup: they stay as they are, a board in the backup with the same id is left out, and a note says so ("“Trip” is shared with you, so it was left as it is."); a backup can't make one of them the home board. Boards this person shared are restored like their own.
- **Import file…** (on a phone, in the File menu under ⋯): pick a file from another app: Markdown (.md, .markdown: Milanote, Obsidian, Notion, Bear…), text (.txt), a web page (.html, .htm: Evernote or Google Keep exports, saved pages), a JSON export (.json: a Trello board, Google Keep notes from Google Takeout) or a PDF (.pdf). The kind of file is worked out from its name and content. Its cards are added to the current board; nothing already there is changed or replaced.

On an iPhone with BusyAnts on the home screen, the downloads (the picture and PDF too) open the Share sheet (Save to Files) instead.

**Markdown** (a Milanote export reads as it always has, except that bullet lines right under a heading now become list items):

- Each heading becomes a checklist with that title; a heading with nothing under it becomes an empty list. A "# name" line at the very top of the file (the board or page name) is ignored, and so is a "---" block of settings at the top (Obsidian).
- Checklist lines ("- [ ]", "- [x]", "* [ ]") become the list's items, keeping sub-items (up to 6 levels), their order and ticks (ticked items stay where they are, struck through). A blank line between items starts a new list with no title.
- Plain bullet and numbered lines ("- a", "* a", "1. a") right under a heading, or inside a list, also become items (not ticked). Elsewhere they stay part of a note.
- Other text becomes a note (paragraphs kept; bold, strike-through and escape marks removed; links shown as "text (address)"). A note that is only a web address becomes a link card, titled by a heading right above it.

**Text:** a .txt file with headings or checklist lines in it is read as Markdown. Otherwise each block of text between blank lines becomes its own note (a block that is only a web address becomes a link card).

**Web pages (HTML):** h1–h6 become checklist titles; lists (ul / ol / li) become items, keeping nesting; a ticked checkbox in an item ticks it; each paragraph becomes its own note (a heading right above it starts the note, line breaks kept); a paragraph that is only a link becomes a link card; links inside text show as "text (address)". Scripts, styles, menus (nav), the page head, comments, noscript, template, iframe and svg are ignored, and so is a heading with no text (such as a logo). Only web addresses (http, https) are shown after a link's text; other links keep just their text. The page is only read as text: it is never shown, its scripts never run and its pictures and other files are never loaded.

**JSON (Trello, Google Keep):**

- A Trello board export: each open list (in Trello's order) becomes a checklist titled with its name; its open cards become items, ticked when the card is marked complete in Trello; a card's checklist items become its sub-items with their ticks (a card with several checklists gets one sub-item per checklist, its items under it). A card's description becomes a note (the card's name on its first line) placed after its list. Archived (closed) lists and cards are left out; a list with no cards becomes an empty list. Labels, dates, members and attachments are not brought in.
- Google Keep notes (one note per file, or a file holding a list of notes): a list note becomes a checklist titled with the note's title, keeping its ticks; a text note becomes a note, its title on the first line; a text note that is only a web address becomes a link card titled with the note's title. Notes in the bin are left out; archived notes come in.
- Any other JSON, or a .json file that isn't valid JSON (including a BusyAnts backup, which goes through Restore from backup…), adds nothing and says "BusyAnts can only import JSON files from Trello or Google Keep."
- All of it is read as plain text: nothing in the file is run, shown as a web page or loaded.

**PDF:** only the text is read; layout, pictures and tables are lost. A file is read as a PDF by its .pdf name or its content.

- Lines clearly bigger than most of the text (and not too long) are headings: the title of the checklist below them, or the first line of the note below them (an empty checklist when nothing follows). A heading over two lines stays one.
- Bulleted lines ("•", "-", "*", "1.", "1)", and the bullets Word puts in PDFs) and checkbox lines ("☐", "[ ]" unticked; "☑", "☒", "✓", "[x]" ticked; similar marks work too) become items of a checklist titled by a heading right above (or untitled); a line indented under an item is a sub-item, and a wrapped item line joins its item.
- Other text becomes notes: a heading right above starts the note, the lines of a paragraph are joined into one (a word broken with "-" is joined keeping the "-"), and separate paragraphs are lines of the same note; a list, a heading or a new page starts a new note. A note that is only a web address becomes a link card. A page number alone at the top or bottom of a page, set apart in the margin and no bigger than the text, is left out.
- A PDF with no text in it (a scan, or only a page number) adds nothing and says "That PDF has no text BusyAnts can read (it may be a scan), so nothing was added."
- The PDF reader (pdf.js) is loaded only when a PDF is imported, so the app's first load doesn't grow. All of the file is read as plain text: nothing in it is run, shown or loaded.

**Every import:**

- The file has no positions, sizes or colors: cards are laid out loose in up to 4 lanes 20px apart (each card at the bottom of the shortest lane, in file order), starting at the top middle of the screen, or the nearest free space (the board then pans to show them). Once drawn, the lanes are tidied to the cards' real heights.
- The imported cards are selected, so they can be dragged or deleted together. One undo removes the whole import. A file with nothing in it adds nothing.
- A file it can't read (another kind, such as a picture, or a broken or password-locked PDF) adds nothing and says "BusyAnts can’t read that file yet." A file over 5 MB is refused with a short note. At most 300 cards and 2,000 checklist items come in from one file; a longer file adds its first part and says so.

## Blocks: cards and containers

The board holds three card types and containers that stack cards. Cards show no type label; the type is told by content. Cards are always white (loose or in a container); only containers are colored.

**Naming** (owner decision, 2026-10-16): people read "container" everywhere: the toolbar, menus, tooltips, screen-reader names, shortcuts, the tour, the website and this spec. Only what people read changed. Code names, CSS classes, test ids and the saved board format keep "column", so saved boards are untouched; the Claude connector (`mcp/`) also still says "column" in its answers and its `column` setting.

| Block | Content | Color |
| --- | --- | --- |
| Note | Free text; grows taller as you type, never scrolls | White |
| Checklist | Title plus checklist (next section) | White |
| Link | Title, URL field, "Open <domain>" button in a new tab; a picture, video or player above the URL field when the address is one (see "Pictures, videos and web addresses") | White |

**Headers:** cards show a collapse arrow and a small trash can (the same icon and faint color as a checklist item's, red on hover) at the top right (no "2/5 done" count); hovering them shows what they do ("Collapse card", "Delete card (Ctrl+Z brings it back)"; containers the same). With a mouse, these header buttons (collapse arrow and trash can, on cards and containers) show only while the pointer is over that card or container, while it is selected, or while one of its fields or buttons has the keyboard focus (owner decision 2026-10-16); they stay in place while hidden, so nothing shifts. On a touch screen wider than a phone they always show; on a phone (under 600px) they show only on the selected card or container (see "Phone layout"). There is no title band (owner decision 2026-10-16): cards are white with a bold title, loose or in a container. **The title is on the button row** (owner pick "impeccable all", 2026-10-22, job 186): a checklist's, link card's or board card's title (a board card's is the board's name) shares its line with the buttons, taking what they leave and shrinking before they move, so there is no empty band above it and each of these cards is about 30px shorter; the button row grows with a bigger title or bigger buttons and keeps the title centered on the buttons; the comment chip and the 32px buttons stay at the right end. A note has no title, so it keeps its button row; a collapsed card shows its preview there, as before; a container already had its title and count beside its buttons. A color picked in the Color menu tints the header, which now holds the title, lightly (see "Collapse, add, delete, color"); a collapsed colored card is all header, so its color fills the whole card, top to bottom and into the rounded corners, at any collapsed height (owner request 2026-10-21). Containers show the title and count at the left, and the collapse arrow next to the trash can on the right. No move handles and no per-block palette icons.

**Moving**

- Drag any blank part of a card or container to move it; a drag starts after a 5px nudge so a click still just selects.
- The dragged block stays flat (no tilt) with a 2.5px amber border and soft glow.
- Dropping a card fully onto a container inserts it at the pointer position; the container opens if collapsed. Dragging a card out of a container makes it loose.
- **A checklist dropped on another checklist pours into it** (owner request): drag a whole checklist so the pointer is over another loose checklist (its title row or its items; the title row is the one with the card's buttons, since 2026-10-22); that list gets the dashed amber outline and nothing is pushed aside. Letting go moves all the dragged list's items to the end of it, with their sub-items, order and ticks (ticked ones stay ticked, in their place; top-level items with no text anywhere in them are left out), and the dragged list, title included, is gone; the list that took them is selected. One undo brings it back. Lists inside a container don't take a dragged list (dropping there puts it into the container as usual), and nor do collapsed lists, notes or links; several blocks dragged together never pour.
- While dragging, the block follows the pointer exactly; a dashed amber outline shows the grid spot it will land on, and on release it glides there (160ms). Blocks pushed aside also glide. No gliding when the computer is set to reduce motion.
- **The dragged block takes priority, and rows keep together** (owner decision 2026-10-19, "Spring back + row shift"): it lands on the grid spot under the pointer, and blocks in its way make room, previewed live while dragging (except over a list it will pour into, above). Room is made only for where the block is now, worked out from where everything was when the drag started: once it has moved past a block, that block springs back to its own spot. Blocks in the same row as the dragged block (they overlap it by at least half the shorter one's height) slide sideways and keep their left-to-right order, pushing the row-mates beyond them along: those whose middle is left of the dragged block's middle go left, the others right (on a tie, the way the dragged block came from, so dragging a block onto its neighbor swaps them; straight up or down, right). Only row-mates level with the ones being pushed are pushed along, so blocks stacked beside the dragged one move over together. Other blocks in the way move to the nearest free spot. A single dragged card never pushes a container: over a container it drops in, and where it would otherwise cover one it takes the nearest free spot (and its row is not shifted for a spot it won't take). Dragged containers push everything. Several blocks dragged together push what is in their way to the nearest free spot (no row shift).
- **No overlap, ever:** loose blocks keep at least a 10px gap. When a container grows, a block is pasted or a size changes, anything it would cover moves to the nearest free spot. Resizing a block by hand works like dragging (owner decisions 2026-10-19 and 2026-10-21): when it is let go, blocks in its row (level with where it was before the drag) that start at or right of it slide right when its right edge was dragged out, keeping their order, and blocks to its left stay where they are; when its left edge was dragged out, blocks in its row that end at or left of it slide left instead, keeping their order, and blocks to its right stay; when its top edge was dragged up, the blocks above it (ending at or above where its top edge was before the drag, so a taller neighbor beside it that merely starts a little higher is not "above" and slides sideways instead; job 183) that it now covers (or comes within 10px of) move straight up, and so do the blocks above those, while blocks beside and below it stay, even when a corner drag now covers them (a card beside it only slides sideways). Dragging only the bottom edge, or the top edge, slides nothing sideways: a block under it is pushed straight down (job #142). Nothing moves while an edge is still being dragged, so shrinking it again before letting go leaves everything where it was. A corner does both of its edges (the top first). When a block grows (expanding, typing, a container filling up), blocks below it (their top level with or lower than its top) are pushed straight down instead, and so are blocks below those; blocks beside it still take the nearest free spot.

**Resizing**

- Loose cards: bottom-right corner handle sets width and minimum height (content taller than that still grows the card). A collapsed loose card can still be resized: a right-edge strip sets its width, and its corner handle sets width and height (down to just its header, 40px). A collapsed loose card starts as tall as a collapsed container (60px), so collapsed blocks line up; one made taller keeps its header in the middle. Its collapsed height is kept separately, so expanding it gives back its open size, and collapsing it again gives back the collapsed size.
- Containers: corner handle and right-edge strip set the width; cards inside follow it. A collapsed container keeps its right-edge strip, so its width can still be changed. On collapsed cards and containers the strip is tinted on hover. A container with cards is always exactly as tall as its cards (so collapsing cards shrinks it); only an empty container has a minimum height, which the corner handle also sets.
- Cards inside a container cannot be resized and size to their content.
- **From all four sides (owner request 2026-10-21, job #135).** With the mouse or a finger, a loose card, open or collapsed, resizes from all 4 edges and all 4 corners; the older bottom-right handle and right-edge strip stay as they are. A container resizes from its left and right edges and all 4 corners (a collapsed container: left and right edges): they set the width, the corners of an empty container also set its minimum height as before, and a container with cards stays exactly as tall as its cards, so its corners only set the width and it has no top or bottom strip. Cards inside a container still cannot be resized.
  - The grab areas are invisible: strips 6px wide along each edge and 12×12px squares at each corner, inside the block's outline; they stop short of the bottom-right handle and never cover the collapse arrow, trash can, tick boxes or item grips. Clicking into text, drag-to-move and the selection box work as before, and a press in a grab area never starts a move. They are not keyboard stops (the existing handles keep the arrow keys). **Not on touch screens** (pointer: coarse, tablets and phones included; recommended call, job #135): a 6px strip is too thin for a finger and would take presses meant for the board next to the buttons' 44px touch areas, so the grab areas are off there and the older bottom-right handle and right-edge strip stay as they were. Where a header button and a grab area meet, the button wins.
  - The edge opposite the one dragged stays where it is: dragging the left or top edge also moves the block's x or y. It follows the pointer, eases to the grid on release (a size that matches another block's wins, as below, but only a match inside the size limits and, from the top edge, not shorter than its content), keeps the size limits, and one drag is one undo step. A card's top edge stops at its content: a card is never made shorter than its text from the top.
  - Where blocks make room on release is described under "No overlap, ever".
- Keyboard: a resize handle reached with Tab resizes with the arrow keys: → / ← 20px wider / narrower, ↓ / ↑ taller / shorter (corner handles only); Shift for 100px. Each press is one undo step.
- While resizing, the edge follows the pointer and eases to the grid size on release; the size label shows the final size.
- Size limits: cards 200–1280 wide, containers 240–1280 wide (owner choice 2026-10-16; was 640), heights 100–700. "Same width" and the keyboard resize use the same limits. Boards already saved are not changed.
- Size matching: within 8px of another block's width or height, the size snaps to match; matched blocks get a dashed amber outline and a label shows e.g. "240 × 180 · same width as 2 blocks". Otherwise sizes snap to the grid when snapping is on.

**Collapse, add, delete, color**

- Collapse arrow: a card shrinks to one line with a preview (first line, list title, or link title), shown in the middle of the card when it is loose; a container hides its cards.
- Collapse all (in the toolbar's Arrange menu; on a phone in ⋯): if any card or container is open, collapses every card and container; when everything is collapsed it reads Expand all. With cards or containers selected it acts on just those (a selected container with its cards), and on everything only when nothing is selected. Collapsing closes the gaps (Collapse all, and also collapsing a single card or container with its arrow): each block below a collapsed one moves straight up by as much as that block shrank, keeping the spacing it had under it (the mirror of growth pushing straight down); blocks to the side and big deliberate gaps stay as they were. Expand all opens every card and container (also ones that were collapsed before Collapse all). Straight after Collapse all it also puts every block back where it was, unless it was moved in between; whatever an opening block grows into is pushed straight down (the higher block keeps its place). One undo step each. Faded on an empty board.
- Same width (in the Arrange menu, after Collapse all; on a phone in ⋯): the selected loose cards and containers all take the width of the first one selected (within each kind's size limits; cards inside containers follow their container). One undo step; anything they now cover moves out of the way. Faded with fewer than two selected.
- Expanding a card or container can push nearby blocks aside. Collapsing it again puts those blocks back where they were (in the same undo step), unless one has been moved since or its old spot is now taken. This is remembered until the page is reloaded.
- Adding a card with a container selected puts it at the end of that container; with a card inside a container selected, directly below that card; otherwise loose on the board. New checklists and containers start untitled, showing a "List title" / "Container title" placeholder (a list made by dropping items on the board too). A new checklist starts with one blank item and the cursor in its title; Enter there moves the cursor to the first item. A new note gets the cursor in its text, a new container in its title. An empty board shows a centered hint ("Add a note, a checklist or a container from the toolbar, or drag one onto the board. Press ? for keyboard shortcuts."; on a phone: "Tap the Add button (+) below to add a note, a checklist or a container.") until anything is on it. Escape leaves the field and keeps the block selected.
- The container's trash can, on a container with cards, opens a small confirmation saying what goes ("Delete “Ideas” and its 3 cards?"; for several containers "Delete 2 containers and their 5 cards?") · Keep container · red Delete container, and then deletes the container and all its cards, with the Undo message. An empty container is deleted at once, with the Undo message (owner, 2026-10-22).
- Toolbar Color recolors every selected container from 24 swatches (three rows of 8 large 32px chips, table below: two rows of soft pastels, then a row of 8 bold, clearly different colors, each ringed in its own edge tone; if the open menu would cover the block being colored, the board moves down so it stays in view), plus Default (back to stone-gray). The name of the swatch under the pointer (or of the current color) shows under the swatches. For selected cards, which stay white, it lightly tints their header instead (and a checklist's or link's title just under it): 60% of the swatch's background mixed with the card's own color, with the usual dark ink (at least 7:1 on every color, light and dark mode); on a bold color the header's icons and the empty title's placeholder use the color's own text color (at least 4.5:1). A note gets the tint across its header strip. Default takes the tint off. A card in a colored container is not tinted unless it is given a color itself. The Color button opens its menu even with nothing selected; the swatches and Default are then faded and do nothing.
- Auto-color, a button at the bottom of the Color menu (below the swatches and Default), gives every container on the board a different color in one step (undoable). Containers are taken left to right, and colors handed out in this order so neighbors differ clearly, the bold colors first: Ocean, Tomato, Emerald, Violet, Sunflower, Magenta, Grass, Tangerine, then the pastels Sky, Peach, Mint, Lavender, Butter, Teal, Rose, Lime, Periwinkle, Coral, Aqua, Orchid, Sage, Sand, Slate, Stone. Colors repeat only beyond 24 containers. It works with nothing selected, and is faded when there are no containers. There is no separate Auto-color button on the toolbar or in the phone ⋯ panel.

### Text formatting

- Every text box can be formatted as a whole: card titles (checklists and links), note text, checklist items and container titles. Not a link's address, nor the board name. Formatting always covers the whole box, never single words (the Journal panel alone has rich text: see "Daily journal").
- Choices: size Small / Normal / Large (Normal is the usual size; they scale with A− / A+, so Large stays larger than the text around it), **bold**, *italic*, and a typeface: Plex Sans (the usual one), Serif, Rounded, Handwritten, Typewriter. No colors (except the Journal's highlight).
- Highlighting any text in a box shows a small bar just above it with B, I, the three sizes and a Font menu (each font shown in its own style). Its buttons format the whole box; hovering the bar outlines what it will change. With checklist items selected, the bar shows above them and formats all of them.
- **The bar from the keyboard** (job 174, owner said "u8 u9 yes", 2026-10-22): while the bar shows, **Alt+F10** moves the keyboard into it (on the first button, Bold; nothing happens when no text is highlighted and no items are selected). Inside it, Left / Right walk along the buttons, Tab and Shift+Tab go round them and never out to the board, Enter or Space presses one. Enter on Font opens the Font menu with the keyboard on the current typeface; Up / Down move in it, Enter picks one (the keyboard goes back to the Font button, the bar stays), and Escape closes just the menu. Escape anywhere else in the bar puts the keyboard back in the text it came from, with the highlighted text still highlighted; Escape in the bar never clears the selection or closes a panel behind it. While the keyboard is in the bar, board keys (Delete, Backspace, tool keys, Ctrl+A, Ctrl+B / Ctrl+I and so on: the bar has its own buttons) don't act on the board; undo, redo and zoom still do (the bar follows its text, and goes if that text is gone). Clicking elsewhere with the mouse still closes the bar. Listed in the ? panel under Text.
- While typing: Ctrl+B bold, Ctrl+I italic, Ctrl+Shift+> larger, Ctrl+Shift+< smaller, on the box you are in (with or without highlighting). With checklist items selected, they format those items; with whole cards or containers selected, every text box in them. Bold and italic turn on for all unless all already have it, then off for all.
- Formatting is saved with the board, syncs, is one Ctrl+Z step, and is kept by copy, duplicate and paste. Enter keeps it on both halves of a split item (and on the new item below); joining two items keeps the first one's formatting. Ticked items and items in the Completed panel keep it. Text copied to other apps is plain.

### Pictures, videos and web addresses

Owner request, 2026-10-19 (job 124): "add the functionality of users being able to add in images, videos, urls by dragging them in, or by copy pasting them in", with no new item type for it. The owner chose that **nothing is uploaded**: a picture or video is shown from its web address, and it is an ordinary link card.

- **Paste a web address** (http or https, alone on the clipboard) anywhere on the board, not while typing in a text field and not while a panel covers the board or an old version is shown: a **link card** appears with that address, selected, in the selected container (as Add does), else loose at the free spot nearest the middle of the screen (like a new card). One undo step. The newest copy wins: if the last thing copied was blocks in the app, Ctrl+V pastes them (as before, undoable); if a web address was copied after that, in another tab or app, Ctrl+V makes the link card. (If Paste is re-mapped to another key, that key always pastes the copied blocks; Ctrl+V still handles addresses.) In a text field the paste stays plain text.
- **Drag a web address, link or picture** from another browser tab or window onto the board (not onto a text field): a link card appears with its middle at the pointer (at the end of the container, when dropped on one), selected, one undo step. The address is read from the dragged address list, else the dragged text.
- **A file from the computer** (a dropped or pasted image or screenshot) is not supported and nothing is stored: a short note says "Images from your computer can’t be added yet. Paste a web address instead."
- **What a link card shows**, decided from its address each time the card is drawn (nothing extra is saved, so saving, sync, backups and every other part of the app are unchanged; it also means that a link card already on a board, shared with the person or imported, whose address is a picture or video shows it from now on): an address ending in .jpg, .jpeg, .png, .gif, .webp, .avif or .svg (a query string is ignored) shows the picture, fitted to the card's width, with the title as its alt text; a YouTube address (youtube.com/watch?v=, youtu.be/, youtube.com/shorts/) shows a player from youtube-nocookie.com and a Vimeo address (vimeo.com/<number>) a player from player.vimeo.com, in a sandboxed frame that allows only what playback needs; an address ending in .mp4 or .webm shows a video with controls (only its first moments are loaded until it is played). Anything else is the ordinary link card. A picture or video that fails to load is not shown: the ordinary link card stays, never a broken-image icon. A player the provider refuses to show (an embed switched off, say) shows the provider's own message: a page in a frame can't be told apart from one that loaded. The title, address box and Open link stay on the card in every case.
- **Only http(s) addresses**, ever: a javascript:, data:, file: or other address is never pasted, dropped or shown as a picture, video or player (an address already typed in a card's address box is checked the same way). A paste does nothing while the Journal or Habits panel is open, or while an old version is shown.
- **Clicking a player:** until its card is selected, a click on a video or player selects (and can drag) the card; once the card is selected, the video or player works as usual.
- The website loading the picture or video can see that it was viewed (said in the privacy page). Copies of a board, backups and exports hold only the address.

## Checklists

A checklist is an editable title plus a tree of items up to 6 levels deep. A ticked item stays where it is, struck through and faded (owner request 2026-10-23, job 200: there is no Completed section inside a list any more); Clean up moves ticked items out.

**Items**

- Item text is edited in place and wraps onto new lines at the width of the card, less the strip kept free at the right for the hover buttons (described below); no focus rectangle.
- Enter works like a text editor. At the end of an item it adds a new item directly below: right after it, or as its first sub-item if it has sub-items. In the middle of the text it splits the item: the text after the cursor moves into a new item directly below (placed the same way; one space at the split is dropped; any sub-items stay with the first half; a ticked item stays ticked in both halves), with the cursor at its start. At the very start of an item with text it adds a blank item right above, and the cursor stays with the text. Selected text is removed first. There is no "Add an item" field and no add or sub-item buttons.
- Tab nests an item under the one above; Shift+Tab moves it out a level. An open item never sits under a ticked one (owner yes 2026-10-22, job 183, so Clean up cannot sweep up an item that was never ticked): when Tab (one item or several), or a drag nested under or dropped among the sub-items of a ticked item, puts an open item there, the ticked items it is under are unticked, as when an item is sent back from the Completed panel, in the same undo step. Backspace on an empty item deletes it (a list's last item, or its last open item, cannot be deleted this way, so the cursor always has an open item to go to). Delete with the cursor at the very end of an item pulls the item shown below it up into it: its text is joined on (cursor stays at the join) and its sub-items move up one level into its place. A ticked item is joined like any other: the joined item stays ticked only when both were ticked, and if that leaves an open item under a ticked one, the ticked items it is under are unticked (job 200).
- On hover, each item shows a trash can (28px wide) and a drag grip (18px), both 28px tall, side by side at the right end of its first line, in a **46px strip** every item keeps free for them (owner pick "impeccable all", 2026-10-22, job 186; it replaces the 2026-10-04 rule that reserved a 40px strip, later 72px, then 92px for all four buttons, which left the text 97px of a 226px card's 202px row). The item's text gets the rest of the row (143px on a new card), so most items fit on one line, and the buttons never cover the text and the text never moves on hover. **Move up and Move down** (22px wide arrows, 28px tall) sit in a small pill (8px rounded corners, a thin edge and a soft shadow, the surface color) at the right end of the row, touching the row's top edge from above, so it lies over the 46px strip the row above keeps free and never covers that row's text; the pill is exactly the strip's width, two 22px arrows. The first item of a list has the card's title row above it, so its pill is just **below** the row instead. The pill fades in with the hover (120ms) and goes when the pointer leaves the row and the pill; it takes no presses while hidden, and a list or sub-item with nowhere to move (a one-item list, a lone sub-item) shows no pill. **Everything grows with the A− / A+ text size step** (owner request 2026-10-21: every width, the icon, the strip and the pill are multiplied by the step, 100% for Small and Normal, 115% Large … 175% Largest, so never under these sizes, but **stopping at 190%** (the strip is 87px, the trash 53px wide, the grip 34px; owner call 2026-10-23: at 400% the tick box alone is 80px, and it, its gap and the strip must fit the 174px row of a 200px card without the box covering a button); the height is the item's first line, which keeps growing, 28px at Normal, 43px at Largest, 58px at 250%, 88px at 400%; the press areas scale with them and stay at least 24×24px; the per-text sizes inside a card don't change them, and the phone layout keeps its sizes; on a touch screen wider than a phone the trash, grip and their strip scale the same way). None shows otherwise (a keyboard-focused one shows too, with a focus ring: tabbing to Move up or Move down shows the pill). The arrows do what the phone's Move up / Move down buttons and Ctrl+Shift+Up / Down do (next bullet), in one undo step, and leave the cursor in the moved item; at the top or bottom of the item's level its arrow is faded and does nothing. On a touch screen (no hover) the pill never shows (the phone has its row above the keyboard) and the strip stays its old, narrower width (40px), with the trash (24px) and grip (14px) at their old, smaller sizes; the grip shows only on the item being typed in, where it drags with a finger, and so does the trash can on a tablet; on a phone there is no trash can on the row (see Phone layout).
- A checklist item's tick box is centered on the middle of the item's first line of text (then nudged down by 5% of the line, 1px at Normal and 2px at 200%, so it reads centered on lowercase text; owner request 2026-10-23), for items and sub-items, at every A− / A+ step and per-text size, in light and dark (owner request 2026-10-21). **The tick box grows with the A− / A+ step** (owner request 2026-10-23: "the checkbox size themselves should also scale appropriately"), by the text step (100% for Small and Normal, 115% Large … 250% … 400% at the top step): **20px** at Small and Normal (owner request 2026-10-23: "the checkboxes can be still a bit bigger"; it was 16px, about 1.25 times bigger), 50px at 250%, 80px at 400% (the tick mark inside grows with it, and so does the pressable area around it, 4px of padding at Normal), never under 20px, ticked or not, on a computer and a tablet. The box takes row width: in a 200px card at 300% and up it and the strip for the item buttons leave the item's text almost no room (it wraps a letter at a time, or shows none), so widen the card at the top steps; the box never covers the text or a button. The phone layout keeps its 16px box and its 44px-wide pressable area.
- **Everything on a card or container grows with the text size step** (owner request 2026-10-23: "font size should affect everything, including the completed and clean up, etc."): the text and the controls that sit in a card or container, by the multiplier of the step (text) and the same never-under-today's step the buttons use (heights and icons): a checklist's Clean up button, a link card's address box and Open link button, a board card's count and Open board button, the question that asks "Delete container?" / "Delete completed items?", and the dragged item's label ("Drop to make a new list" and the other hints). Card and container titles, notes, item text, the collapsed card's preview and a container's count already did. The phone keeps its button heights but its text follows the step. At the smallest card (200px) and container (240px) widths at 400%, nothing runs over its card's edge: from 225% up, a card’s buttons (Clean up included) drop to a line below its title when they would cover it (the title keeps at least about two and a half letters), and a collapsed card's preview gives way to its buttons. Item text in such a narrow card wraps to a few letters a line (none at 300% and up, beside the tick box), so at the top steps widen the card; cards are never widened by themselves.
- Up / Down arrows move between items as if the list were one long text: Up goes to the end of the item above, Down to the start of the item below. Inside a multi-line item they move line by line first. Ticked items are visited like any other.
- Ctrl+Shift+Up / Down move the item being typed in (with its sub-items) past the item above / below at the same level, keeping the cursor in it, past ticked and open items alike; at the top or bottom of its level nothing happens.
- Ctrl+Enter (⌘+Enter on a Mac) in an item ticks it, exactly as clicking its Done box does (it stays in place; the same sub-item rules, selected items and one undo step); on a ticked item it unticks it and the cursor stays where it was. After a tick the cursor moves to the nearest open item below it in the same list (an open sub-item of the ticked item counts), or else the nearest one above; with no open item left it leaves the field and the list stays selected. It never splits the item or adds one.

**Ticked items and Clean up** (owner request 2026-10-23, job 200)

- Ticking an item, top-level or sub-item, leaves it where it is: its text is struck through and faded, its tick box is ticked, and nothing else moves. Unticking puts it back to normal, in the same place. The sub-item rules are unchanged: ticking the last open sub-item of an item ticks that item too (and so on upwards), and unticking a sub-item unticks the items it is nested in. A tick applies at once, with no animation. One undo step.
- **Clean up** in a list's title row: a small text button, shown only while something in the list (top-level or sub-item) is ticked and the list is open. It does the Arrange menu's Clean up for this list only: its ticked items, with everything nested under them, move into the board's Completed panel under today's date (see "Clean up and the Completed panel"); other lists are left as they are. The list stays selected. One undo step. It grows with the A− / A+ step like the other title-row buttons (60px wide, 12px text at Normal) and fits a 200px card at every step. It never squeezes the title (owner request 2026-10-24, job 208): when the title, Clean up, the collapse arrow and the trash can all fit on one line, Clean up sits between the title and the collapse arrow; when they don't, Clean up drops onto its own short line under the title, at the right of the title column, and the title keeps the full width it has without Clean up, with the arrow and trash can staying on the title's line (at the biggest text steps in the narrowest cards the buttons can still drop to a line below, as they do for any list). It is hidden on view-only boards and in exported pictures. On a touch screen it is pressed from 44px wide and as tall as the header's other buttons' press areas, never covering the comment chip's or the collapse arrow's drawn box; on a phone it shows only on the selected list, like the collapse arrow and trash can (job 113), so a tap there on another list only selects it.
- There is no Uncheck all any more (owner request 2026-10-23: "The uncheck all functionality is no longer needed").
- **Ctrl+Shift+Backspace** (with the Control key on a Mac too, since ⌘+Shift+Backspace there is the browser's Clear browsing data; not while typing in a text field) deletes every ticked item on the open board, top-level or sub-item, with everything nested under it (job 200; before, only the Completed sections' items). Other boards (sub-boards too), open items and the Completed panel are left alone. It always asks first, below the toolbar in the container confirmation's style: "Delete 12 completed items?" ("Delete 1 completed item?"; the count includes sub-items) · Keep · red Delete. Escape keeps them, and other board keys wait until it is answered. Delete is one undo step: Ctrl+Z brings them all back. A list left empty gets one blank item. With nothing ticked, nothing is deleted and a short note, "No completed items on this board", shows for a moment. On a shared board it works like any other edit. It does nothing while an old version is being looked at.
- Older saved boards keep a per-list "Completed section open" setting; it is still saved, so the saved format is unchanged, but it is no longer used, and loading never reorders items.
- Web addresses (http://, https:// or www.) typed in a note show as links under its text (the address without https:// and www., opening in a new tab); Ctrl+click (⌘+click) on an address in a note or a checklist item opens it too.
- Trash deletes that item and everything nested under it. If a list becomes empty, a blank item replaces it.
- Exception: deleting an item with no text (trash, Backspace or Delete) keeps its sub-items if any of them has text; they move up one level into its place. Cut (Ctrl+X) always takes sub-items with the parent.

**Dragging items**

- Drag the grip to move an item and all its sub-items: before/after another item (amber line), nested under an item (drop slightly right; amber tint), into another list, or anywhere else inside a list's box (the empty space under its last item, the title row; appends at the end; the whole card, top included, gets a dashed amber outline). Over the item rows themselves, before / after / nested still applies (owner request 2026-10-23, job 194).
- Dropping on empty board space (or on a note, link or open container) creates a new untitled checklist at that spot with the dragged items, in the colour of the list they came from and as wide as it is (its height just fits the items; a list that sits in a container has no width of its own, so then the new list gets the usual width; owner request 2026-10-23, job 203) (the dragged label says "Drop to make a new list", and only says it when the pointer is outside every checklist's box). Dropped on a collapsed checklist, they go in at its end (ticked ones stay ticked); it stays collapsed and gets the dashed amber outline while they are over it. Dropped on a collapsed container, they become a new untitled checklist at the end of that container, which opens.
- A list emptied by the drag (every item dragged out, one at a time or several selected, into another list or onto the board) is gone, title or not, and the list that took them is selected. One undo brings it back.
- **Lifting an item on a phone (owner request 2026-10-19, job 114).** On the phone layout (under 600px wide, by finger), resting a finger on a checklist item (its text included) for about half a second lifts it, and moving then drags it with its sub-items, with the same drop rules as the grip (before, after or under another item, into another list, onto empty list space, onto the board as a new list). The grip still drags at once. While it is held: the item leaves its place; its label is drawn as a floating row, as wide as the item, with a shadow under it, on the finger's line a little above it and kept on the screen (the label of a grip drag on a computer is unchanged); the rows slide smoothly aside, up to close the space the item left and down to open a gap of its height where it would land (in another list too; over empty board or over nothing only the first happens); and the board's edge panning works as for the grip. Letting go drops it where the gap is, and the rows stay where they slid. A quick tap on an item still types, and a finger that moves before resting moves the board, as for a card. Resting on the text being typed in (the item, title or note that has the cursor) never lifts or picks anything up, on any touch screen: that is the phone's own cursor moving and selecting; a swipe on it still moves the board (job 197). A lift, an item or card drag or a resize whose finger is lost without its lift-off reaching the page ends by itself, with nothing changed (the item, card or size stays where it was): at the next touch that starts with no other finger on the screen, or when the page is hidden, for example by switching apps (job 197). Resting on the list's title, the card's blank parts or a note still picks up the whole card. Windows 600px and wider (tablets too) are unchanged: resting on an item picks up the card. Only `transform` and `opacity` move (the label moves by `translate`, never `left` / `top`); with the computer set to reduce motion the rows jump at once and the label does not grow in. The cursor is not changed (build rule 6). The drag is view only until the drop: the drop is the usual one undo step.

**Selecting several items**

- Hold the mouse on one item and drag over others to select a range, across open and ticked items. Shift+click extends the range; with no range yet, Shift+click selects from the item being typed in to the one clicked. A range can span items at different levels. Selected items get a amber text highlight and a lighter row tint. No action bar.
- With several selected: Backspace or Delete removes them all; ticking any one ticks them all (unticking one reopens them all); the trash on any one deletes them all; dragging any one moves them all, in order, with their sub-items; Ctrl+C / Ctrl+X / Ctrl+V copy, cut and paste them after the selection. Copy and cut take exactly the highlighted items (a sub-item that isn't highlighted is left out, and cut leaves it in the list, moved up into its parent's place), and also put their text on the computer's clipboard for other apps: one item per line in the order shown, indented two spaces per level below the least-indented highlighted item; Tab / Shift+Tab move them all in or out one level together (one that can't move, such as the first item of a list, stays and the ones after it nest under it) and they stay selected; Escape clears.
- Ctrl+A, pressed again and again, selects more each time: first the text of the item being typed in; then every item in that list (from some of a list's items, the whole list); then every item in every list in the same container (skipped for a loose list); then every item on the board. Only items you can see are taken: none from collapsed cards or containers. Escape or clicking empty board clears.
- Pressing on an item and dragging down or up into another card of the same container carries the selection on through those cards (never into other containers or loose cards).
- With items selected in several lists: Delete / Backspace, ticking and the trash work on all of them (a list left empty keeps one blank item); Ctrl+C copies them, putting each list's title on its own line with its items indented two spaces under it, in board order (containers left to right, each top to bottom, then loose lists top to bottom, left to right). Tab, Ctrl+X, Ctrl+V and dragging do nothing then.

## Keyboard navigation between cards

- Up / Down arrows move through every text field of a card (note text, list title and items, link title and address). Inside a container they carry on into the card above or below and select it. Collapsed cards are skipped; loose cards don't continue to other cards.
- Alt + arrow keys jump to the nearest card or container in that direction by on-screen position (loose or in a container), select it, put the cursor at the end of its first field and pan it into view. Only a card or container lying wholly that way counts (one mostly below is reached with ↓, never →); one straight ahead (level with it for ← / →, above or below it for ↑ / ↓) beats one off to the side, then the nearest wins. Containers are stops at their title strip: ↑ from a container's top card goes to the container (cursor in its title), ↓ from there to its first card, ← / → from a title to the next container's title; empty and collapsed containers are reached the same way. With nothing selected they start from the card or container nearest the middle of the screen. Works while typing.
- Ctrl + arrows keep moving word by word in text. Alt + ← / → never make the browser go back or forward a page.

## Version history

- Like Google Docs, earlier versions of the board are kept and can be looked at and restored. On a computer it opens from the History button (a clock with the label "History") in the panel pill bottom right; on a phone from ⋯ → Version history.
- A version holds every board. A version is saved automatically: when editing starts again after 10 minutes without an edit on any board, every board as it was just before is saved (and during a long stretch of editing, once an hour). Undo and redo count as edits; blocks re-arranging themselves don't. A version that couldn't be saved (offline, say) is tried again a minute later. The board on screen is always the "Current version". Changes arriving from another device don't save a version there (that device saves its own), with one exception (job #147): when such a change replaces one of this person's own boards that were already here, and this page has had edits since it last did this, every board as it was just before the change is saved as a version first, so work done here that an older copy replaced (say one a phone saved offline and sent hours later) can be brought back. In the list it reads "Before changes from another device" before what was on the boards. It is saved at most once every 10 minutes (so using two devices at once doesn't fill the history), never for a shared board someone else changed or a shared board arriving, and if it can't be saved (over the 900,000-character online limit, say) the incoming change still goes ahead. Only an open page can keep it: a page opened after the change arrived only sees the new copy. - **Tools that change boards (job B, 2026-10-07):** only on the owner's own boards; a shared board is refused ("shared boards are read-only for this connector"), also one just shared whose old copy is still in the owner's own boards. A share never makes one of the owner's other boards read-only (job 192; the owner's own boards win, exactly as the app decides): one of the owner's board ids counts as shared only in a share of their own, as the board they shared (the share's fixed starting board) or a board inside it, never Home; a share whose starting board is one of the owner's ids holds nothing. Boards and checklists are named by id, or by name when only one has it (otherwise the choices are listed); items by id. Each call is one save and answers with a plain list of what changed ("Saved:" then one line each, with new items' and notes' ids), or an error, with nothing saved.
  - `add_items(board, list, items[{text, after?, under?}])`: at the end of the checklist, right after an item (several after the same item keep their order), or as the last sub-items of an item. Text is one line (line breaks become spaces), never blank.
  - `edit_items(board, changes[{item, text}])`: new text. There are no due dates (removed 2026-10-16): a `due` sent to `add_items` is ignored, and `edit_items` changes only text.
  - `set_items_done(board, items[], done)`: ticks or unticks, as clicking the box does (the last open sub-item ticks its parent).
  - `move_items(board, items[], to{list, after? | before? | under?})`: with their sub-items (each list's items in the order shown, lists in the order their items were given), to a checklist on the same board; never next to or under themselves. A list the move empties keeps one blank item (moving never deletes a list).
  - `add_note(board, text, column? | near?)`: at the end of a column (id or title), just below a card in a column or beside a loose card or column (`near`: its id), or else loose near the top left, never over another block. Notes can only be added, not edited.
  - **Making things (job 110, 2026-10-19):** `add_checklist(board, title, items[]?, column? | near?)` adds a checklist placed as `add_note` places a note (with no items it gets one blank item, as a new checklist in the app; at most 50 items). `add_column(board, title, near?)` adds an empty column (the app's container) beside a card or column, or else near the top left, never over another block. `create_board(name, inside?, column? | near?)` makes a new, empty, named board: inside one of the owner's boards, with a board card opening it there (placed as a note is), or else on its own, as New board in the app does (then `column` and `near` are refused). There is no tool for link cards (no Add Link anywhere, owner decision 2026-10-05).
  - **Deleting (job 110, 2026-10-19), two steps:** `preview_delete(board, things[])` lists exactly what would go and deletes nothing; `confirm_delete(preview)` then deletes exactly that, once, after the person has said yes. Things are items (with their sub-items), cards, columns (with their cards; the Completed card stays, loose, as in the app) and boards inside this board (with their cards; boards inside them are kept and then stand alone, as in the app), by the ids `read_board` shows; at most 20 ids per call (a column or a board counts as one). It uses the app's own delete functions (`deleteItems`, `deleteBlocks`, `withoutBoard`), so a checklist emptied of items keeps one blank item. Never deleted: the home board, a top-level board (home, or a board no card opens), the Completed card, or anything on a shared board, or anything that would change one. Previews are kept in memory only: each is used once and works for 10 minutes, and a restart of the connector forgets them (a confirm refused because deleting is off or the board can't be read leaves the preview for a retry). If anything the preview would delete has changed since (any of its text, ticks, items or cards, even what the list doesn't show, or something more or less would go), nothing is deleted and a new preview is needed; changes elsewhere, such as renaming the board, don't stop it.
  - **"Let Claude delete" setting:** off by default. It is `settings.json` beside the saved sign-in (`%APPDATA%\busyants-mcp\`), on that computer only, not in the boards or synced. Only the owner switches it, with `npm run mcp:delete-on` / `npm run mcp:delete-off`; no tool can. It is read again on every delete call, so switching it off works at once. While off, both delete tools answer that deleting is switched off and only the owner can switch it on. `npm run mcp:check` shows "Claude may delete: yes / no".
  - Items nest at most 6 levels. At most 50 changes per call and 5,000 characters per item or note text.
- **Saving a change:** the connector reads the owner's boards, makes the change with the app's own rules (`src/model/`), and saves only if every board still passes `problems(board)`, the boards are safe to edit (`safeToEdit`; old, damaged or newer-app data is refused) and the saved text is at most 900,000 characters. It saves `data`, its own `client` name (`mcp-…`) and the server's time, only if nothing was saved since it read (Firestore's `updateTime` condition); if something was, it reads again and makes the change on top, at most 3 more times, then gives up ("the boards kept changing"), saving nothing. Nothing in Firestore is ever deleted: a delete removes things from the saved boards, with a backup version saved first.
  - **Safety version:** before its first change (and again when a change comes after 10 quiet minutes, or an hour after the newest version, as the app's version rule), the boards as they were are saved as a version (board text first, then its list entry, never over an existing one), unless the newest version already holds exactly that (`contentHash`). If the version can't be saved, the change isn't made. Before every delete one is always saved (no 10 quiet minutes needed), again on each retry when the app saved in between, so the newest version holds the boards just before the delete; `confirm_delete`'s answer says it is in Version history (the History button). The app keeps the newest 100 versions, so such a backup goes once 100 newer ones are saved.
  - **Put back:** 5 seconds after saving it reads the boards again. If the app saved over the change (own boards sync "most recent wins"), it makes the change once more on top (same ids, so nothing doubles) and says so; if it is saved over again, the answer says the change isn't on the board now, and it isn't tried a third time. If the board changed so the change no longer applies (its list deleted, say), the answer says so and nothing is put back. Known limit: if the owner changes the same item in the app within those seconds, the connector's change is put back over it. A delete is never put back: if the app saved the deleted things back, the answer says so and they stay (a new preview is needed to delete them).
  - **Activity log:** every save is added as a plain line with the time to `%APPDATA%\busyants-mcp\activity.log`.

## Search

- Ctrl+F (also while typing in a card) opens the board's own search bar instead of the browser's; so does the Search button (a magnifier with the label "Search") at the left of the panel pill (bottom right), and ⋯ → Search on a phone. The bar sits at the top right (across the top on a phone).
- It looks in container titles, list and link titles, checklist items (sub-items and ticked items too), notes, link addresses and the Completed panel, ignoring upper / lower case. Matches are taken in board order: containers left to right (their cards top to bottom), then loose cards top to bottom.
- Every match is marked in yellow inside the text, the current one in orange; the bar shows e.g. "2 of 7", or "No matches". Enter / ↓ / the down arrow button go to the next match, Shift+Enter / ↑ / the up arrow button to the previous one (wrapping round). The board moves so the current match is in the middle of what can be seen (above a phone's keyboard), zooming in to 60% first (not 100%; owner request 2026-10-19: it zoomed in a bit too much) if the board is zoomed out below 60%; at 60% or above the zoom is left as it is.
- A match out of sight (in a collapsed card or container) marks that card or container with an orange ring instead, and the count says "in a closed card"; nothing is opened by itself. A match in a link address rings the address box.
- Matches in the Completed panel come after all the others. While the panel is shut, the current one rings the Completed button and the count adds "in Completed"; the panel is not opened by itself. While it is open, the match is marked in the panel and scrolled into view.
- Escape (also with the keyboard on one of the bar's buttons, and then never closing a side panel behind it) or × closes the bar and the marks go. Typing in the box, only the zoom keys (Ctrl + = / − / 0) reach the board; Ctrl+F does nothing while the keyboard shortcuts list is open (it may be recording a key) or the welcome tour is up.
- **This board / All boards** (owner request 2026-10-19, job 102): under the box a two-option switch, "This board" and "All boards" (two toggle buttons; 28px tall on a computer, 44px on a phone; the bar's colors). The bar opens on "This board" every time it opens, and the choice is view state: never saved, not undoable. Escape or × closes the bar and the next search starts on "This board" again (Ctrl+F while the bar is already open keeps what is chosen). Clicking an option leaves the cursor in the box, so Enter still steps.
  - **All boards** counts matches on every board the person has, sub-boards and the hidden Journal and Habits boards included, with the same match rules as above (board names themselves are not searched). The open board comes first, then the other boards in the Boards menu order (sub-boards under their board); inside a board, board order as above. The order is fixed when the box, or the switch, last changed, so stepping through it does not reshuffle it when a match opens another board. A board that is not among the person's boards (a shared board they can't open) is not searched.
  - The count reads e.g. "3 of 12 · Garage" while the current match is on another board that is not open (for example the first match when the open board has none); the board does not move until you go to the match (Enter or Shift+Enter first goes to that current match). Enter / ↓ / the arrow buttons go to the next match, and Shift+Enter / ↑ / the up arrow to the previous one (wrapping round, across boards); a match on another board opens that board the way the Boards menu does (same undo and selection behavior), then the board moves to the match and marks it as above. Opening a board by hand does not change the list.
  - Searching only reads: it never changes or saves a board. (Opening a board by search has the Boards menu's one side effect: leaving a new, empty, unnamed board that nothing opens discards it, as the menu does.) Going back to "This board" limits matches to the open board again.
